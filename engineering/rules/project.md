# 项目工程规则入口

本文件定义 `rag-knowledge-platform` 的通用红线。AI 应渐进加载规则，不要把所有规则一次放入上下文。

## 加载顺序

1. `.ai/project.json` 与 `.ai/current-role.md`
2. 本文件
3. 当前角色对应的 `roles/<role>.md`
4. 当前任务对应的 `checklists/<task>.md`
5. 模块需求、设计、API 契约和附近代码

## 全局规则

1. 开始前检查 Git 状态，保留用户已有改动，只修改当前任务相关文件。
2. 当前角色的允许、确认和禁止路径优先于任务清单。
3. 功能文档放在 `docs/modules/<module>/`，需求、设计、API、任务、测试、运维和支持分目录维护。
4. 同一功能只有一份权威 API 契约；前后端类型、字段、枚举、分页、权限和错误处理必须对齐。
5. 控制器/路由层保持轻量，业务逻辑进入服务或领域层；前端请求进入独立 API client，不在页面散落地址和协议细节。
6. 危险操作、SQL、权限、部署和外部系统调用先预览、说明影响和回滚方式，再按授权执行。
7. 新增依赖、公共抽象和跨模块改动前先搜索现有能力并评估影响面。
8. 不提交秘密信息；日志、截图和测试数据在交付前检查脱敏。
9. 生成文件通过生成器维护，人工文档不得被全量刷新静默覆盖。
10. 无法完成验证时必须如实记录，不能把“未发现”表述为“已通过”。

## 契约优先流程

`requirements -> design -> api-contract -> backend -> frontend -> test -> delivery`

需求和契约未就绪时，可以调研、列差异和提出方案，不应猜测关键业务字段后直接完成实现。

## 验证原则

- 运行与改动范围匹配的最小有效命令，优先聚焦模块或文件。
- 业务逻辑需要自动化测试；可见 UI 变化需要行为验证，条件允许时保留截图。
- 交付时列出执行过的命令、结果、跳过项、环境限制和残余风险。
