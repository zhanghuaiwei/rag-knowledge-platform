# 通用企业知识库平台技术选型

> **文档状态**：评审中 · **版本**：v0.2.0-design · **负责人**：待指定 · **最近更新**：2026-08-10
> **权威范围**：技术职责、默认适配器、替换边界与 ADR；具体字段见 [`04-数据库设计.md`](04-数据库设计.md)，部署拓扑见 [`06-架构方案.md`](06-架构方案.md)。

## 1. 选型原则

1. **能力与接口先于产品名**：领域层依赖端口，默认实现只是可替换 adapter。
2. **安全和治理是硬约束**：身份、ACL、数据分类、驻留、审计和法律保全不可因 provider 不支持而静默降级。
3. **减少真相源**：PostgreSQL 管业务事实，对象存储管不可变内容；索引、缓存和统计均可重建。
4. **先满足当前规模，再保留扩展路径**：目标基线为单租户 2 万文档、约 100 万 chunk；避免为未知规模提前微服务化。
5. **版本可复现**：锁定 major/minor/镜像 digest/BOM，禁止生产使用 `latest`；升级由兼容矩阵和回归门禁驱动。
6. **标准优先**：OIDC/OAuth、SCIM、S3 API、OpenAPI、OpenTelemetry、SQL migration 优先于私有协议。

## 2. 结论总表

| 领域 | 默认选择 | 可替换边界 | 主要理由 |
| --- | --- | --- | --- |
| 领域服务 | Java 21 LTS + Spring Boot/Security/Data | `service` 内 ports/adapters | 企业生态、事务、OIDC resource server 与运维成熟 |
| RAG/解析 | Python 3.12+ + FastAPI + provider-neutral pipeline | rag-engine ports | 文档/模型生态丰富，易隔离重计算任务 |
| Web | Node.js Active LTS + Next.js App Router + TypeScript | OpenAPI 生成 client | BFF/OIDC、SSR/流式体验、类型契约 |
| 业务数据库 | PostgreSQL 16+ | SQL 标准 + migration | 事务、JSONB、约束、PITR、RLS |
| Schema 管理 | Flyway（server 启动外或 CI/CD migration job） | 标准版本化 SQL | 替代人工顺序脚本，提供 checksum、历史和失败状态 |
| 对象存储 | S3-compatible ObjectStore port | MinIO/云 S3 API | 版本、保留、生命周期和私有化可移植 |
| 搜索索引 | `SearchIndex` port；默认 OpenSearch | Milvus+关键词索引、pgvector | BM25、向量、过滤、高亮、alias 在一个派生索引完成 |
| 缓存/协调 | Redis-compatible Cache port | Redis/Valkey | TTL、限流、短期策略快照与轻量协调；不作事实源 |
| 异步一致性 | PostgreSQL transactional outbox + worker | Kafka/Pulsar/Redis Streams | MVP 无双写窗口；规模增长后替换 transport |
| 身份 | 外部 OIDC Authorization Code + PKCE | SAML bridge；SCIM 同步 | 支持 MFA、企业 IdP 与最小凭证暴露 |
| 服务身份 | mTLS + workload identity/短期凭证 | SPIFFE/SPIRE、mesh、云工作负载身份 | 不信任网络位置，支持轮换和审计 |
| 解析/OCR | Parser/OcrProvider | PyMuPDF/Unstructured、PaddleOCR、云 OCR | 格式和部署环境可替换，定位元数据一致 |
| 模型 | Embedding/Reranker/LlmProvider | 本地、云端、客户模型网关 | 数据分类/区域/成本/健康策略统一路由 |
| 内容安全 | ContentSafetyProvider + quarantine | ICAP/AV、ClamAV、DLP/secret scanner | 恶意文件和敏感内容在解析/外发前阻断 |
| 可观测性 | OpenTelemetry + Prometheus-compatible metrics | OTLP backend、Grafana/供应商 APM | trace/log/metric 统一关联，减少自定义链路字段 |

## 3. 核心方案比较

### 3.1 应用架构：模块化单体 + 独立计算引擎

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 模块化单体 server + rag-engine/workers | 本地事务清楚、交付简单；计算负载可独立扩缩 | 需严格模块边界 | **默认** |
| 全微服务 | 独立发布扩容 | 契约、运维、数据一致性成本高 | 仅在实测瓶颈后拆分 |
| 单一进程 | 开发最简单 | Python/Java 生态与重计算隔离差 | 不采用 |

原 v0.1 的 Seata AT 被移除：KB 与成员写入位于同一 PostgreSQL 时应使用本地事务；对象存储、搜索索引和模型调用无法靠 Seata 获得真正原子性，应使用 outbox、幂等消费者和补偿任务。

### 3.2 搜索：统一 SearchIndex 与可选专用向量引擎

| 方案 | BM25/高亮 | 向量/融合 | 复杂过滤/alias | 运维复杂度 | 适用 |
| --- | --- | --- | --- | --- | --- |
| OpenSearch | 原生 | 支持 k-NN/混合 | 强；可原子切 alias | 中 | **默认企业规模** |
| Milvus + 独立关键词索引 | 需双索引 | 强 | 标量过滤强，但双索引一致性复杂 | 高 | 超大向量规模/专用场景 |
| PostgreSQL + pgvector | 需自建全文配置 | 可用 | 事务近、扩展简单 | 低 | 小规模/边缘私有化 |

决策：领域只依赖 `KeywordIndex` 与 `VectorIndex/SearchIndex` 能力。默认 adapter 使用 OpenSearch，把关键词、向量、过滤、高亮和索引 alias 统一为一个派生系统；需要专用向量引擎时由 adapter 组合 Milvus 与关键词索引，不改变业务状态模型。

OpenSearch 的索引 alias 用于换模/重建原子切换；embedding 在 rag-engine/provider 生成，避免搜索集群直接持有外部模型凭证。

### 3.3 多租户隔离

| 层 | 机制 | 说明 |
| --- | --- | --- |
| 身份 | tenant 来自验证后的 OIDC/session/API Key | 不接受 body/header 自报 tenant |
| 应用 | SubjectContext + PDP/PEP | 每个资源用例检查 tenant、scope、角色与文档策略 |
| 数据库 | `tenant_id` + 复合外键 + CHECK | 阻止跨租户关联写入 |
| 数据库纵深 | PostgreSQL RLS（可选启用） | runtime role 默认拒绝；migration owner 绕过 |
| 对象存储 | tenant/KB/version 命名 + bucket/KMS 策略 | 高敏租户可物理隔离 |
| 搜索 | tenant + allowedDocumentIds/policy snapshot 预过滤 | ACL 收紧不依赖异步索引更新才生效 |
| 数据驻留 | `document.data_region ?? kb.data_region ?? tenant.data_region`（C7 决策） | 高敏内容不得路由到不满足驻留策略的 provider；KB 创建时继承租户区域 |

### 3.4 身份与授权

- 浏览器登录：OIDC Authorization Code + PKCE；优先 BFF + Secure/HttpOnly/SameSite cookie。
- API 资源：Spring Security OAuth2 Resource Server 校验 issuer、audience、signature、exp/nbf；角色不是资源授权的替代。
- 机器访问：client credentials 或带 `scope + allowedKbIds + expiry` 的高熵 API Key。
- 身份生命周期：`issuer + subject` 为外部身份主键；全局用户与租户成员分离；组织/组允许多归属；SCIM 为 P1。
- 文档权限：allow-list；文档 ACL 存在时覆盖 KB 继承；权限分为 excerpt/content/original-download。

不再提供 Resource Owner Password Credentials grant；本平台不自建用户密码认证作为企业默认路径。

### 3.5 事件与一致性

- 业务事务同时写 domain row 与 `outbox_event`；dispatcher 成功发布后标记状态。
- 消费者按 eventId/idempotencyKey 去重；失败指数退避，达到上限进入 dead letter。
- 事件 transport 起步可由 PostgreSQL SKIP LOCKED worker 实现；流量、跨区域或多消费者需求明确后切 Kafka/Pulsar。
- Redis Pub/Sub 不作为可靠事件真相源。

### 3.6 内容处理

- Quarantine object 先执行真实 MIME、大小/层级、恶意软件、DLP/secret 与提示词注入风险检查。
- Parser 输出统一 `ContentBlock{text, location, type, metadata}`；location 可表达 page、section、slide、sheet/cell、line。
- OCR 是 provider 能力而非阿里云前提；私有化默认允许本地 OCR，云 OCR 受数据分类和区域策略约束。
- 分块策略按文档类型/profile 版本化，不再只保留全局 `chunk_size`。

### 3.7 模型与索引配置

- `index_profile` 固定 embedding provider/model/revision/dimension/normalization、chunker、语言 analyzer 和 metric。
- ACTIVE profile 不可原地修改；换模建立新 profile + index build + quality gate + alias switch。
- LLM route 与 embedding profile 分离。LLM 可在请求间路由；embedding 不可按请求或用量直接切换语义空间。
- provider route 同时检查 sensitivity、dataRegion、purpose、budget、timeout 和健康；不合规 provider 不进入 fallback 集合。

## 4. ADR

### ADR-1：采用模块化单体 + 独立 rag-engine/workers

- **状态**：接受。
- **理由**：当前规模下减少分布式复杂度，同时隔离 Python/模型/解析负载。
- **后果**：模块只能通过 application port 或事件协作；禁止跨模块直接写表。

### ADR-2：用本地事务 + outbox 替代 Seata AT

- **状态**：接受，替代 v0.1 ADR-1。
- **理由**：关系库内操作无需分布式事务；外部索引/对象/模型不能由 AT 保证原子性。
- **后果**：所有外部副作用必须幂等、可重放、可补偿并可观测积压。

### ADR-3：默认 SearchIndex 采用 OpenSearch adapter

- **状态**：接受；Milvus 保留为可选 adapter。
- **理由**：当前规模下统一 BM25、向量、过滤、高亮和 alias，减少双索引一致性面。
- **后果**：做容量/召回/过滤压测；索引 mapping 由 profile 生成并版本化。

### ADR-4：身份交给企业 OIDC，授权留在领域层

- **状态**：接受。
- **理由**：支持 MFA/SSO/生命周期；避免平台持有企业密码。
- **后果**：需要 IdP 配置、tenant membership 映射和 SCIM/SAML 扩展端口。

### ADR-5：全局身份 + 租户成员 + 多组织关系

- **状态**：接受。
- **理由**：一个人可加入多个 tenant/组织，适配 SaaS 与集团组织。
- **后果**：旧 `sys_user.tenant_id/org_id/role` 进入兼容期，迁移后由 membership 表取代。

### ADR-6：原始内容和版本不可变

- **状态**：接受。
- **理由**：支持来源、审核、引用、回滚、法律保全和删除证明。
- **后果**：更新创建新 version；document/current alias 只切指针。

### ADR-7：Schema 由 Flyway 管理

- **状态**：接受，替代纯手工顺序脚本。
- **理由**：需要 checksum、历史、锁和失败可见性。
- **后果**：`deploy/ddl/init.sql` 保留新装初始化源文件（单文件一键），`deploy/compose/` 编排中间件；生产由 migration job 执行，不由应用运行账号建表。

### ADR-8：OpenTelemetry 作为链路标准

- **状态**：接受。
- **理由**：跨 Java/Python/worker/provider 统一 trace 与 baggage，避免只靠日志字段拼接。
- **后果**：敏感 tenant/user 信息不得无控制进入第三方 observability backend。

### ADR-9：内容安全是摄取门禁

- **状态**：接受。
- **理由**：企业知识库输入和 RAG 上下文均来自不可信文件/外部源。
- **后果**：扫描不可用时新内容停留 quarantine；结果和规则版本可审计。

## 5. 版本与兼容策略

| 组件 | 版本策略 | 红线 |
| --- | --- | --- |
| JDK | 21 LTS 基线 | 不跨 LTS 升级而不做 JVM/依赖/性能回归 |
| Spring Boot/Security | 选择仍受维护且兼容 JDK 21 的 release line，由 BOM 锁定 | 不手工混用不兼容 Spring 模块版本 |
| Python | 3.12+，由 lockfile 固定 | 解析/ML 原生依赖需有目标架构 wheel/镜像验证 |
| Node.js | Active LTS；Next.js 使用受支持 stable line | 不使用浮动 tag，不绕过 lockfile |
| PostgreSQL | DDL 以 16+ 语法为基线 | major 升级先验证 extension、RLS、PITR 和 query plan |
| SearchIndex | 选择受维护 release 并固定 image digest | 不允许 adapter 依赖未声明的实验字段/DSL |
| Redis-compatible | 固定 major/minor | 不把缓存/stream 当唯一事实源 |
| 容器/模型 | digest/revision/checksum 固定 | 禁止 `latest`、运行时从不可信 URL 下载模型 |

升级流程：安全/生命周期检查 → 兼容矩阵 → isolated build → contract/migration/retrieval/security/performance 回归 → canary → 观察 → 扩大；失败时回切旧制品和索引 alias。

## 6. 需要在实现前实测的决策

- OpenSearch 与 Milvus adapter 在授权过滤比例 2.5%/40%/80%、100 万与 1000 万 chunk 下的 Recall@K/P95/成本。
- PostgreSQL RLS 对高频列表、批量同步和管理查询的开销，以及连接池 tenant context 清理。
- 不同解析/OCR provider 对中文、表格、扫描件、PPTX/XLSX 的定位准确率与数据外发约束。
- OIDC BFF 与纯 SPA 的部署边界；默认推荐 BFF，最终由 Web/安全评审冻结。
- 首批内容安全 adapter、DLP 分类级别、数据区域与外部模型允许清单。
